VBR Lab

A live player that reads the next few seconds

In April, Netflix’s live streaming team wrote that every Live event now uses capped VBR, and that they’re testing whether devices can choose streams using the actual sizes of upcoming segments instead of nominal bitrates. I built a simulator to see what that buys a player, and what it costs.

The question comes from Netflix’s post Smarter Live Streaming at Scale (April 2026).

Try it

Two simulated players watch the same live event over the same network. They use the same decision rule. The only difference is what each one believes the next segments will cost: the nominal bitrate on the label, or the real size the server has already published.

A third player, drawn dashed, is a reference from published research: the buffer-based design from Netflix and Stanford’s 2014 paper “A Buffer-Based Approach to Rate Adaptation”. It ignores throughput and picks bitrate from buffer level alone. Change the event, the network, or the encoding, and all three rerun.

The simulator needs JavaScript to run.

What I found

With CBR, the two players are nearly identical. That’s the sanity check: when the label matches reality, knowing the real size adds nothing. Flip the encoding to CBR in the simulator to see it.

With capped VBR on a volatile phone connection, the size-aware player rebuffers less. It sees an expensive scene, like a fight starting or confetti falling, in segments that are already published, and steps down before the spike drains its buffer. The nominal player only finds out after the download is slow.

On steady Wi-Fi neither player stalls. There the size-aware player mostly saves data, at a small cost in quality, because it stops reaching for a top rung whose real segments have become expensive. It isn’t free, though: it switches bitrate more often, since real segment sizes jump from scene to scene. A production version would need to weigh smoothness, which my rule only handles crudely.

The buffer-based player draws a sharp line between the two networks. On steady Wi-Fi it’s the best of the three: the highest quality, the fewest switches, and no stalls. On busy evening Wi-Fi it still has the highest quality and almost no stalls, though it uses roughly 15 to 25 percent more data. On a phone connection it reaches about 7 to 9 points higher quality but stalls three to six times as long. The paper’s buffers were four minutes long. Live allows about 8 seconds, so by the time the buffer reveals a slowdown, there’s little left to spend. In this model, that’s the case for looking ahead at what’s coming instead of waiting for the buffer to fall.

How it works

A control problem

I study mechanical engineering, so I read adaptive bitrate as a feedback controller. The buffer is the state. Network throughput is a noisy disturbance. The rung you pick each segment is the control input, and a stall is the failure you’re designing against. VBR adds a second disturbance the player can partly see in advance: how expensive the content is about to be.

The stream

A six-rung ladder from 400 kbps to 8 Mbps, cut into 2-second segments. Each event is a sequence of scenes with a compression difficulty, from a static waiting room to confetti. Under capped VBR, a segment’s real size follows that difficulty and is capped at 1.6 times nominal, with higher rungs swinging more. Under CBR it stays within 10% of nominal.

The player

It joins four segments behind the live edge and can’t download a segment before it exists, which keeps the buffer short, as it is in real live playback. Playback starts after two segments. Throughput is estimated as the harmonic mean of the last five downloads, so one fast download can’t inflate it.

The shared decision rule

For each rung from the top down, the player plays the next three segments forward at 90% of estimated throughput and picks the highest rung that keeps the buffer above 2.5 seconds. It steps up at most one rung at a time, and only with 2 extra seconds of margin. The nominal player prices each segment at its label. The size-aware player uses the real size of every segment already published, and for segments past the live edge it assumes the latest real-to-nominal ratio, never less than nominal.

The buffer-based reference player

This is BBA-0 from the paper. At or below 2 seconds of buffer (one segment), it takes the lowest rung; from 7 seconds up, the highest. In between, a straight line maps buffer level to a target rate, and the player moves only when that target crosses the next rung up or down, which keeps it from flickering. The paper used a 240-second buffer and reached the top rung at 90% full. These thresholds were set the same way from the 8-second live cap, not tuned on results.

What this leaves out

The numbers are illustrative, not Netflix data. The quality score is a stand-in tied to each rung, not VMAF. Network traces are synthetic. It models one viewer, not the server side, so it ignores Netflix’s other next step: reserving server capacity with a discount informed by real VBR behavior. It also assumes the server can tell the player the sizes of segments it has already encoded.

What I’d do next

Replace synthetic scenes with real per-segment sizes from an open VBR encode, score quality with Netflix’s open-source VMAF, and add a server with many viewers to explore the capacity-reservation question. I’d also add the paper’s BBA-1, which handles variable bitrate by mapping buffer level to upcoming segment sizes instead of nominal rates. It’s a buffer-based version of the same idea the size-aware player tests.

The simulator is plain JavaScript with no dependencies. It has unit tests, including the CBR sanity check above. Read the code on GitHub.
